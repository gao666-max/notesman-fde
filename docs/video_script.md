# 产出 4：5 分钟讲解视频脚本

## 0:00-0:30 开场：核心矛盾

笔记侠编辑团队面临的核心矛盾不是"AI 能不能写"，而是编辑的注意力该花在哪里。

一份 90 分钟的访谈逐字稿有 97 个段落。编辑现在的工作流程是：通读全部 97 段，手动标注有价值的地方，搭建文章结构，分段写作，反复返工。最耗时的环节不是写作，是在大量低信息密度的口语对话里找到那几个真正值得写的观点。

负责人说过一句话：我不要一个把录音转成文章的工具，我需要 AI 帮编辑更快找到真正值得写的观点，保留证据，形成可编辑的内容初稿。最后一层判断，仍然由编辑完成。

这就是我设计的起点。

## 0:30-1:20 四 Agent 架构

我设计了一个四 Agent 的框架，每个 Agent 只做一件事：

Agent 1 观点提取——读逐字稿，输出 10 到 15 个结构化的观点节点，每个附带证据原文、时间戳、置信度，自动归类到五个抽屉里。

Agent 2 历史复用判断——把观点和历史笔记做匹配，标注哪些旧内容可以引用、哪些是陷阱。比如面试题数据包里 note_02 和当前逐字稿是同一场访谈，Agent 2 会标记"同一场，不复用"。

Agent 3 内容生成——基于编辑选定的观点和大纲，生成 500 到 800 字的可编辑初稿。

Agent 4 事实核查——逐条比对草稿里的论断和原始证据，输出红黄绿三级优先级的核查报告。

一句话总结：AI 负责信息处理——提取、匹配、对比。编辑负责判断——什么值得写、什么不能写、怎么说才对。

这个分工体现在哪呢？编辑不在聊天框里跟 AI 对话，而是在一个可视化的面板上看到 AI 预处理好的观点卡片，拖拽、排序、选择。编辑做的是决策，不是打字。

## 1:20-3:10 Demo 演示

好，现在看实际操作。

【打开页面】

这是一个预置好演示数据的页面，面试官打开就能看到完整交互。

【指四象限】

中间这个四象限图，纵轴是置信度，横轴是热点相关性。绿色卡片在右上角——高置信加高热点，可以直接采用。黄色在中间——建议复核。红色在左下角——必须编辑确认。编辑一秒钟就能判断重点在哪，这是第一层效率提升。

【指卡片库】

左侧是卡片库，分五个抽屉。这里有一个设计上的思考——一篇好文章的价值通常来自三个方向：高维思想是认知升级，当下解答是实用价值，信息差是你不知道但应该知道的。所以 Agent 1 提取观点时会自动判断每一条属于哪一类，装进对应的抽屉。还有两个特殊抽屉——弱信号，嘉宾提过但没展开的；低置信度，AI 拿不准的留给编辑决定。

四象限告诉你"这张卡片质量如何"，五个抽屉告诉你"这张卡片讲的是什么"，两个视角叠加，编辑可以快速定位。

【点击卡片】

我们点击一张卡片看看。弹出来的详情包括证据原文、时间戳、置信度说明。往下翻，这是一个因果链面板——如果嘉宾的表述里有"因为 A 所以 B 导致 C"的逻辑，Agent 1 会自动提取出来，编辑一眼就能看到推理步骤有没有断点。旁边是反观点——同一场另一个嘉宾对这个问题有不同看法的话，这里会标注出来，帮助编辑看到对话里的张力。还有原文上下文——这个观点在逐字稿里前后是什么语境，不用翻原始文件。

【导入 SRT】

现在演示导入真实的 SRT。点"导入 SRT"，选题目提供的 interview_transcript.srt。Agent 1 开始分析，大概 30 到 50 秒。分析完之后四象限和卡片库会换成全新的数据，标题和段落结构也由 Agent 1 自动建议。

【拖拽卡片】

好，分析完成了。我把一张卡片拖到编辑工作区，再拖一张。点"生成全文草稿"——Agent 3 把这两张卡片展开成一篇 600 多字的文章。标题来自嘉宾原话里最有冲击力的一句，编辑可以直接在上面改。

【事实核查】

点"事实核查"——Agent 4 逐条比对，输出核查报告。每条标注了优先级——红的是必须确认，黄的是建议确认，绿的是可以后续处理。每个问题都给了具体的改写建议，编辑照着改就行。

【导入历史笔记】

还有一个功能——导入历史笔记。点"导入历史笔记"，选 historical_notes.jsonl，Agent 2 自动判断哪些旧内容可以复用、哪些是陷阱。

## 3:10-4:05 关键取舍

现在说三个关键取舍。

第一个，为什么用多步 Prompt 链而不是 Agent 框架？因为这四个 Agent 的输入输出是确定的——观点提取就是 SRT 进去、JSON 出来。Prompt 链更可控、更容易调试，单个模块出问题直接定位。但架构上每个模块是独立的——将来想换成 LangGraph 或 CrewAI，换的是调用方式，不是整个设计。

第二个，Agent 2 的同一场检测。这是我实际踩过的一个坑。最开始 Agent 2 是一个 prompt，让它同时判断"是不是同一场"和"能不能复用"。结果 LLM 认出了同一场但还是给 95 分判复用——因为"内容高度匹配"这个词同时触发了加分和拒用两个相反的动作。Prompt 改了好几版都不行。最后我把架构拆成了两阶段——Phase 1 只做同一场检测，结果在代码层直接排除，Phase 2 再对剩下的笔记做语义匹配。同一个信号不会再触发两个相反动作了。这个教训是：不要靠 prompt 死磕一个内在矛盾的判断，该改架构就改架构。

第三个，为什么目前没有 RAG 外检？方案里规划了完整的路径——Embedding 加向量检索加可信源验证。48 小时内搭向量数据库风险太高，当前用 LLM 训练知识做交叉验证，能诚实地标注"这个数据我没见过，需要编辑核实"，不冒充实时检索。

## 4:05-5:00 如果有更多时间

如果有一周而不是 48 小时，我会做三件事。

第一，给 Agent 4 接上真正的 RAG 外检。当前能告诉编辑"这个数据我无法确认"，但不能自己去查。RAG 管道搭好之后，像"终生收入下降五分之一"这种嘉宾引用的外部数据，系统能自动搜索可信来源给出验证结果。

第二，Agent 2 的规模化。现在几十篇笔记全塞进上下文没问题，但上百篇就得在前面加一层向量初筛——先把候选从 100 篇缩到 20 篇，再让 LLM 做精细判断。方案已经设计好了，缺的是实现时间。

第三，协作功能。现在是一个编辑对着自己的卡片做决策。如果多个编辑同时在线——有人负责筛选观点、有人负责结构、主编做最终拍板——每个人对同一个素材的判断不一致，这个"不一致"本身是有价值的信息。把它记录下来、变成可追溯可讨论的，就是从个人工具到团队平台的关键一步。

谢谢。
