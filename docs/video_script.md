# 产出 4：5 分钟讲解视频脚本

## 0:00-0:30 开场：我看到了什么

"笔记侠编辑团队面临的核心矛盾不是'AI能不能写'，而是编辑的注意力该花在哪里。

一份 90 分钟的访谈逐字稿有 97 个段落。编辑当前的工作流程是：通读全部 97 段 → 手动标注有价值的地方 → 搭建文章结构 → 分段写作 → 反复返工。最耗时的环节不是写作，是在大量低信息密度的口语对话里找到那几个真正值得写的观点。

负责人说：'我不要一个把录音转成文章的工具。我需要 AI 帮编辑更快找到真正值得写的观点，保留证据，形成可编辑的内容初稿；最后一层判断，仍然由编辑完成。'

这就是我设计的起点。"

## 0:30-1:30 我设计了什么

"我设计了一个四 Agent 架构，每个 Agent 只做一件事：

Agent 1 观点提取：读逐字稿 → 输出 10-15 个结构化观点节点，每个附带证据原文、时间戳、置信度和热点匹配。
Agent 2 历史复用判断：把观点和历史笔记做相似度匹配，标注哪些旧内容可以引用、哪些是陷阱——比如面试题数据包里 note_02 和当前逐字稿是同一场访谈，Agent 2 会标记'同一场·不复用'。
Agent 3 内容生成：基于编辑选定的观点和大纲，生成 500-800 字的可编辑初稿。
Agent 4 事实核查：逐条比对草稿中的论断和原始证据，输出 🔴🟡🟢 三级优先级核查报告。

AI 负责信息处理——提取、匹配、比对。编辑负责判断——什么值得写、什么不能写、怎么说才对。

这个分工体现在交互设计上：编辑不在聊天框里跟 AI 对话，而是在一个可视化面板上看到 AI 预处理好的观点卡片，拖拽、排序、选择。编辑做的是决策，不是打字。"

## 1:30-3:00 Demo：核心路径演示

"【屏幕录制：打开浏览器 → localhost:3000】

这是预置的演示数据。面试官打开就能看到完整交互。

【点击一张绿色卡片】
每张观点卡片点开是一个详情弹窗——左侧是证据原文和时间戳，往下滚是"原文上下文"面板——编辑可以看到这个观点在逐字稿中前后的完整对话，不用翻原始文件。

【展示四象限】
四象限全局概览——纵轴是置信度，横轴是热点相关性。绿色是可直接采用的，黄色是建议复核的，红色是必须编辑确认的。编辑一眼就能判断优先级。

【拖拽演示】
现在我来演示导入真实 SRT 的流程。点击'导入 SRT'，选择题目提供的 interview_transcript.srt。Agent 1 正在分析——大约 30-50 秒。分析完成后，四象限和卡片库会换成全新的真实数据。标题和段落结构也由 Agent 1 自动建议。

【拖一张卡到工作区】
我把两个观点拖到编辑工作区。点'生成全文草稿'——Agent 3 生成一篇 600-850 字的文章。标题'AI不会淘汰你，但会淘汰那个只想被夸的人'直接来自嘉宾原话。正文里嘉宾称呼有变化、段落间有因果递进、关键数据用了审慎表述。

点'事实核查'——Agent 4 逐条比对，输出核查报告。每个问题标注了优先级。

还有一个功能：导入历史笔记。点'导入历史笔记'选 historical_notes.jsonl，Agent 2 判断复用。"

## 3:00-4:00 关键取舍

"三个关键取舍：

第一，为什么用多步 Prompt 链而不是 Agent 框架？因为这四个 Agent 的输入输出是确定性的——观点提取就是 SRT 入、JSON 出。Prompt 链比 Agent 框架更可控、更可调试。但架构设计保留了多 Agent 的模块化——每个模块独立可替换。方案文档里有如果迁移到 LangGraph 或 CrewAI 的技术路径。

第二，为什么 prototype 里没有 RAG 管道？方案设计里规划了完整的 RAG 外检流程——Embedding → 向量检索 → Top-K=5 → LLM 判断。但 48 小时内搭向量数据库风险太高。当前原型用 LLM 训练知识做交叉验证，方案文档标注了'这是替代实现'。

第三，为什么 LLM 的非确定性不是 bug？同一个 SRT，Agent 1 跑两次结果不完全一样——观点的选择、措辞、排序会有差异。这恰恰证明了编辑判断不可替代：如果 AI 的输出本身就不确定，那么最终取舍就必须由人来完成。"

## 4:00-5:00 如果有更多时间

"如果有一周而不是 48 小时，我会做三件事：

第一，给 Agent 4 加上真正的 RAG 外检管道。当前原型用 LLM 训练知识做交叉验证——能标注'这个数据我没见过，需要编辑核实'，但不能自己去查。方案里规划了完整路径：Embedding → 向量检索 → 可信源验证，缺的主要是搭管道的工程时间。

第二，Agent 2 的规模化。当前方案每次把所有历史笔记塞进上下文让 LLM 判断，笔记量几十篇的时候完全够用。但如果到了上百篇，需要在 Agent 2 前面加一层向量初筛——先把候选范围从 100 篇缩到 20 篇，再让 LLM 做精细判断。架构方案已设计，缺的是实现。

第三，给前端加上协作功能。现在是一个编辑对着自己的观点卡片做决策。如果有多个编辑——比如有人负责观点筛选、有人负责结构搭建、主编做最终拍板——每个人对同一个素材的判断不一致其实是有价值的信息。记录这种判断差异、让它可追溯可讨论，是从'个人工具'到'团队平台'的关键一步。

谢谢。"
